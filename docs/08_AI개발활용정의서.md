## 0. 요약 — 단계별로 쓴 기법 · 도구와 그 사용법

> 발표·보고서에 그대로 옮길 수 있는 분량으로 줄인 것. 근거와 수치는 1~8장.

### 1. 기획 — 말로 흩어지는 요구를 번호로 고정

1. **도구 / Claude Code** : 인터뷰 녹취와 받은 자료를 넣고 정리시켜, 흩어진 이야기를 주제별로 묶었다.
2. **기법 / 질문 목록화 (Q-xx)** : 모르는 것은 바로 가정하지 않고 번호 붙인 질문으로 뽑아, **현장에 물을 것**과 **가정하고 갈 것**을 갈랐다.
3. **기법 / 결정 번호화 (D-xx)** : 답이 온 것은 결정마다 번호 · 근거 · 영향 문서를 한 줄로 적었다. 이렇게 쌓인 **결정 100건이 뒤 단계 전부의 기준**이 된다.
4. **기법 / 명세 우선 원칙** : 명세와 코드가 다르면 명세가 기준이라고 `CLAUDE.md`에 못 박아, AI가 코드를 보고 명세를 바꾸지 못하게 했다.
5. **결과** : PRD · 기능 · 화면 · 데이터 명세 7개 문서.

### 2. 설계 — 말 대신 시안으로 고르게, 고른 것은 토큰·규칙으로 굳히기

1. **도구 / unslop 스킬** : 디자인 방향과 색·글꼴·간격 체계를 잡는 데만 썼다 (다듬기는 뒤 단계의 impeccable이 맡도록 역할을 갈랐다).
2. **기법 / 시안 여러 개를 나란히 비교** : 말로 설명하는 대신 **HTML 시안 54개와 비교 페이지**를 만들어 사용자가 직접 고르게 했다. 고른 결과는 다시 D-xx로 남겼다.
3. **기법 / 토큰화** : 고른 방향의 색·간격·글꼴을 **CSS 변수 한곳(`tokens.css`)**에 모으고, 컴포넌트는 색값을 직접 쓰지 못하게 했다. 이유는 `DESIGN.md`에 적었다.
4. **기법 / 구조를 린트로 못 박기** : 층과 의존 방향을 정한 뒤 **ESLint 규칙 9개**로 강제해, 문서를 읽지 않아도 어기면 커밋 전에 걸리게 했다.
5. **결과** : `DESIGN.md` · `tokens.css` · `FRONTEND.md` + `eslint.config.js`.

### 3. 개발 — 백엔드를 기다리지 않고 화면부터

1. **도구 / Claude Code** : 화면 15개, 공용 부품 59개, 데모 공급기, 실서버 어댑터를 구현.
2. **기법 / 계약 1개 + 공급기 2개** : 화면은 데이터 계약(`contracts.ts`)만 알고, 그 뒤를 **데모 공급기와 실서버 어댑터**가 각각 채운다. 덕분에 백엔드 완성을 기다리지 않고 전 화면을 만들었고, **환경 변수 하나로 데모 ↔ 실서버**를 바꾼다.
3. **기법 / 부품 먼저** : 화면마다 새로 그리지 않고 base · charts · domain 3층 부품을 먼저 만들어 재사용했다.
4. **도구 / 서브에이전트** : 넓은 범위를 뒤져야 할 때만 따로 돌려, 본 작업의 맥락을 흐리지 않았다.
5. **기법 / 커밋 전 자동 검사** : `npm run check`(타입 검사 · ESLint · Stylelint)를 통과해야 커밋.
6. **결과** : 5일 101커밋, `src/` 19,727줄.

### 4. 검토 — 사람 눈 대신 점수·대조표로

1. **도구 / impeccable 스킬 (critique · audit)** : 디자인을 **점수와 지적 목록**으로 받았다 (알람 화면 26/40). 전부 받아들이지 않고 **고를 것만 골라** 재설계 결정 D-111로 남겼다.
2. **도구 / `/code-review` · `/simplify`** : 커밋 전 코드의 버그·중복을 훑었다.
3. **기법 / 해상도별 스크린샷 대조** : 1920 · 1440 · 1536 세 해상도로 36장을 찍어 레이아웃이 깨지는 곳을 눈이 아니라 파일로 비교했다.
4. **기법 / 명세 1:1 대조** : 백엔드 **REST 41개**를 프론트 계약과 하나씩 맞춰 보고, 없는 API · 다른 필드를 **411줄 문서**로 정리해 백엔드에 요청했다.
5. **결과** : `API-차이-v3.1.md`, 재설계 결정 D-111.

### 5. 네 단계를 관통한 기법

1. **규칙을 매 세션 자동으로 읽히게** : 지켜야 할 것을 `CLAUDE.md` 53줄로 묶어 세션마다 자동으로 올린다. 길어지면 지켜지지 않으므로 세부는 다른 문서로 내리고 길만 적는다.
2. **규칙을 말이 아니라 검사로 강제** : 층 의존 방향 · 타입 · 스타일을 ESLint · TypeScript · Stylelint가 막는다.
3. **문서를 자동 생성** : 결정 ↔ 코드 역링크 표를 스크립트로 다시 만들어, 사람이 갱신을 잊어 낡는 문서를 줄였다.

**한 줄 정리 — AI가 만들고, 결정은 사람이 하고, 결정은 번호(D-xx)로 저장소에 남는다.**

## 3. 문서 체계 — AI에게 무엇을 언제 읽히나

AI와 일할 때 가장 크게 갈린 부분이다. **문서를 "사람이 읽는 것"이 아니라 "AI에게 읽히는 것"으로 설계**했다.

### 3.1 세 가지 원칙

1. **항상 읽히는 것은 짧게.** `CLAUDE.md`는 53줄로 묶어 두고, 깊은 내용은 따로 두고 길만 적는다. 규칙이 길어지면 매 세션 토큰을 먹고 정작 지켜지지 않는다.
2. **역할을 겹치지 않게.** 무엇을 만드는가(`docs/specs/`), 어떻게 보이는가(`DESIGN.md`), 코드가 어떻게 짜였나(`FRONTEND.md`), 왜 그렇게 정했나(`02_결정사항_미결.md`) — 한 가지는 한 곳에만 적는다.
3. **충돌 순서를 미리 정한다.** 문서끼리 다르면 `CLAUDE.md` → `DESIGN.md` → 스킬 규칙 순. 명세와 코드가 다르면 **명세가 기준**(`CLAUDE.md`).

### 3.2 문서별 역할

| 문서 | 줄 | 언제 읽히나 | 담는 것 | 담지 않는 것 |
|---|---|---|---|---|
| `CLAUDE.md` | 53 | **매 세션 자동** | 상태 색·토큰·관제 화면 성격·문구·코드 규칙, 스킬 역할 분담, 충돌 우선순위 | 화면별 세부 |
| `MEMORY.md` (색인) | 4 | **매 세션 자동** | 기억 한 건당 한 줄 | 기억 본문 |
| `memory/*.md` | 4건 | 색인을 보고 필요할 때 | 사람이 준 지침과 **그 이유** | 저장소에 있는 규칙 |
| `README.md` | 144 | 처음 들어올 때 | 실행법, 문서 지도, 데모↔실서버 전환 | 결정 근거 |

### 3.3 이 방식이 실제로 한 일

- **규칙이 코드로 강제된다**: `CLAUDE.md`의 "층 사이 의존 방향"은 말로만 두지 않고 `eslint.config.js`에 9개 층 import 제한으로 넣었다. 문서를 안 읽어도 커밋 전에 걸린다.
- **문서가 스스로를 고치게 한다**: `05_결정_구현대조표.md`는 손으로 쓰지 않고 `대조표생성.sh`로 다시 만든다. 사람이 갱신을 잊어 낡는 문서를 하나 줄였다.
- **이유까지 적는다**: 검사기 경고를 끌 때도 `.impeccable/config.json`에 왜 껐는지와 누가 판단했는지를 남긴다 (예: "모눈은 공장 배치도 표면에만 씀", "Claude 판단: 이 파일은 화면이 아니라 Word 내려받기용 HTML").

| **위키 링크가 한 방향이었다**: 코드 → D-xx는 주석으로 촘촘했지만(`grep -rn "D-109" src`), 결정 → 어느 파일인지는 매번 찾아야 했다 | `05_결정_구현대조표.md` + `대조표생성.sh` 추가 (50건 역링크) |
| **기억이 코드보다 뒤처지는 일이 실제로 났다**: API 점검에서 "보고서 안 만든 고장" 항목을 결함으로 보고했는데, 그 항목은 D-111로 이미 바뀌어 사라진 것이었다. 코드가 맞고 AI 기억이 낡았던 사례 | 위 역링크 표가 이 점검을 `grep` 한 번으로 줄인다. 글의 "dreaming = 전사 기록과 대조해 틀린 기억 고치기"에 해당 |
| **규칙이 브랜치 사이에서 빠졌다**: 11/19에 모양 규칙 2개(선택 칸에 왼쪽 띠 금지 · 시안 px를 구현에 옮기지 않기)를 기억에서 `CLAUDE.md`로 옮겼는데, 그 절이 `feat/ui-v2`에만 남고 **작업 브랜치로는 넘어오지 않았다**. 기억 파일은 색인에서만 빠져 "있지만 안 읽히는" 상태였다 | 규칙 절을 작업 브랜치 `CLAUDE.md`로 옮기고, 기억 2건은 11/19 결정대로 지움. **기억을 되살리는 게 아니라 저장소로 올리는 쪽**이 이 프로젝트의 방침 |

> **이 셋이 같은 교훈을 가리킨다**: 기억에만 있는 것은 PC·브랜치를 넘지 못한다. 넘어야 할 것은 `CLAUDE.md`에, 결정은 D-xx에, 둘을 잇는 것은 자동 생성 표에 둔다.

### 4.4 글의 발견 중 이 프로젝트와 맞은 것

| 글의 발견 | 이 프로젝트에서 |
|---|---|
| **빡빡한 규칙보다 재량이 낫다** — "실패만 기록" 같은 제한을 두면 이득이 줄었다 | `CLAUDE.md`를 53줄로 짧게 두고 세부는 참조로 내린 구조가 같은 방향 |
| **위키 구조가 성능을 올린다** — 128번의 정리를 거치며 평가 정답률 13% → 48% | 결정 로그 + 역링크 표가 그 역할. 이 프로젝트는 "AI가 혼자 쌓은 위키"가 아니라 **사람이 결정한 것을 번호 붙여 쌓은 위키**라는 점이 다르다 |
| **무엇이 중요한지 가리는 능력** — 전략 파일 10개 vs 413개의 차이 | 기억은 4건만. 저장소에 둘 수 있는 규칙(색·토큰·층·모양)은 기억에 두지 않는다 |
| **주입 맥락은 엄선한다** | 매 세션 올라가는 것은 `CLAUDE.md` 53줄 + 색인 4줄뿐 |

> **보고서에 쓸 한 줄**: 이 프로젝트는 AI에게 "기억하라"고 맡기는 대신, **기억해야 할 것을 저장소 문서로 꺼내 놓고 매 세션 다시 읽히는 구조**를 썼다. 다른 PC에서 작업해도 `CLAUDE.md`는 따라오지만 기억은 따라오지 않기 때문이다.

### 6.3 잘 안 된 것 · 조심한 것 (보고서에 쓰면 신뢰가 올라가는 부분)

- **AI 기억이 코드보다 뒤처진 사례**: 11/20 API 점검에서 이미 D-111로 바뀐 항목을 결함으로 보고 → 4.2에서 역링크 표로 대응.
- **시안 수치를 구현에 그대로 옮기지 않기**: 시안 HTML의 px·여백을 구현에 복사하지 않는다는 규칙을 사용자가 못 박았고, 기억에 남겼다(`wireframes-are-layout-reference`).
- **AI 티 나는 디자인 걷어내기**: 목록 선택에 왼쪽 진한 띠를 쓰는 흔한 AI 패턴을 사용자가 지적 → 가라앉은 면 + 가는 테두리로 바꾸고 기억에 남겼다(`no-left-accent-bar`).
- **지어내지 않기 규칙**: "명세에 없는 기능·수치·문구를 지어내지 않는다. 데모용 값이 필요하면 그렇다고 밝힌다"를 `CLAUDE.md`에 넣고, 화면에 "데모 데이터" 표시를 띄운다.
- **검사기 오탐도 근거를 남김**: impeccable 탐지기 경고를 끌 때마다 이유를 `.impeccable/config.json`에 적었다.
