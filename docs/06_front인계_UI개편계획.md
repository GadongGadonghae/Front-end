## 0. 핵심 목적과 요약

> **이번 개편의 핵심 (D-96)**
> 1. **화면마다 목적이 드러나게 강조한다.** 화면을 열면 "이 화면은 무엇을 보라는 것인지"가 가장 먼저 보여야 한다.
> 2. **가독성을 위해 화면 구성 자체를 다시 짠다.** 색·글꼴만 바꾸는 것이 아니라, 무엇을 크게 두고 무엇을 줄이며 정보를 어떻게 묶을지부터 다시 정한다.
>
> 디자인 톤, 디자인시스템, 도구, 3D는 모두 이 두 목표를 돕는 수단이다. 시안을 고를 때도 이 두 가지를 가장 먼저 본다 (6.4).

기능·데이터·API는 그대로 두고, **디자인 UI와 화면 구성을 처음부터 다시 검토**한다. 받은 피드백(2장)을 시안 공통 규칙으로 삼는다. 실제 대기업 디자인시스템을 하나씩 바탕으로 한 **시안 3개**를 대표 화면 3개에 만들어 지금 시안 B와 나란히 비교한다. 고른 방향으로 DESIGN.md와 화면을 새로 만든다.

## 2. 받은 피드백과 반영 방침 (R-23, D-95)

지금 화면(시안 B 기반 구현)에 대해 2026-11-19에 받은 외부 피드백이다. 원문 요지와 반영 방침을 함께 적는다. 해석이 갈리는 곳은 미결로 남겼다.

### 2.1 UI

| # | 피드백 | 지금 상태 | 반영 방침 |
|---|---|---|---|
| 1 | **폰트 크기를 중요도에 맞게.** 지금은 너무 크고 일관성이 없다. **크기는 큰데 전체 가독성은 떨어진다** | FRONTEND.md 3.4 글자 크기는 커밋 89fdd07에서 9단계 → **5단계**(13·14·20·32·44px)로 이미 줄임. 굵기 600은 여전히 넓게 씀 | **글자 단계를 제목 / 본문 / 보조 3단계 + 숫자 2단계(핵심 숫자·보통 숫자)로 줄이고 전 화면에 통일한다** [가정: 숫자 2단계]. 단계 수는 이미 5개라(A-16), 남은 일은 단계마다 쓰임을 다시 나누고 굵기·대비·줄 간격으로 위계를 만드는 것이다. 크기를 키우는 대신 위계(크기 차이·굵기·색 대비)로 읽히게 한다. 가독성은 줄 간격, 글자 대비(흐린 글자 남용), 한 칸에 담긴 정보량, 굵기 남용을 같이 점검한다 (`/impeccable typeset`·`audit`) |
| 2 | **트리 구조로 만들기.** UI가 투박하다 | 상단 메뉴 + 화면 안 이동 경로(대시보드 > 라인 > 공정, D-82) | **화면 안의 정보 계층을 정리한다** (D-97). 메뉴는 그대로 두고, 화면 안 정보를 공장 > 라인 > 공정 > 설비 순서로 묶어 상위 정보가 먼저, 하위 정보가 그 안에 보이게 한다. 같은 수준의 정보는 같은 모양으로 둔다 |
| 3 | **대시보드가 잘 안 들어온다. 알림은 작게 둬도 된다** | 오른쪽 세로 열 전체가 알림 (D-46) | 알림 열을 줄이고(접기, 최근 몇 건, 또는 헤더 알림으로) 대시보드의 주인공(공장 상태)을 키운다. D-46 변경 |
| 4 | **큰 이슈는 화면에서 더 돋보이게:** 깜빡임, 조치 요청 등. **3D가 더 좋을 수도** | 고장 토스트와 칸 색만. DESIGN.md는 깜빡임·반복 애니메이션 금지 | **큰 이슈 = 고장(D)만** (D-97). 고장이 생기면 해당 설비가 깜빡이고 "조치 요청" 버튼이 나온다. 깜빡임 규칙은 2.3. 3D 뷰(SCR-005)에서도 같은 설비를 강조한다. **예지보전 주의·위험은 큰 이슈가 아니라 별도 영역**에 따로 보여 주고 깜빡이지 않는다 |

### 2.2 화면 설계·산출물

| # | 피드백 | 반영 방침 |
|---|---|---|
| 5 | **목적과 화면 구성이 맞지 않는다.** 의도한 부분이 확 드러나게 화면 설계를 고친다 | 화면마다 **목적 한 줄과 주인공 칸 하나**를 먼저 정하고(6장 3단계), 시안은 그 주인공이 가장 먼저 눈에 들어오게 배치한다. 시스템 목적은 기능명세서·PRD의 배경·목표에서 가져온다 |

### 2.3 깜빡임 규칙 (피드백 4와 D-93 "화려하지 않게"를 함께 지키는 방법) [가정]

산업 HMI 관행(ISA-101): **확인하지 않은 큰 알람만 깜빡이고, 확인하면 멈춘다.** 평소 화면은 조용하게, 이상이 생긴 곳만 확실하게 드러나게 한다.

| 규칙 | 내용 |
|---|---|
| 대상 | 진행 중인 **고장(D)** 설비만 (D-97). 대기(I)·정지(S)·해제된 건, 예지보전 주의·위험은 깜빡이지 않음 |
| 조치 요청 | 고장 설비 옆(배치도 칸·알림·토스트)에 버튼. 누르면 시뮬레이터에서 그 설비 상태가 바뀌고(예: D → R 복구) [가정: 바뀌는 상태], 고장이 아니게 되므로 깜빡임도 멈춘다. 지금은 데모 시나리오를 움직이는 용도이며 실제 백엔드로 보내지 않는다 (D-97). `VITE_DATA_SOURCE=api`일 때는 버튼을 숨긴다 [가정] |
| 속도 | 1초에 3번 미만 (WCAG 2.3.1 번쩍임 기준). 테두리나 칸 밝기만 바꾸고 화면 전체가 번쩍이지 않게 |
| 1초 갱신과 구분 | 값 갱신 때 깜빡이는 효과는 여전히 쓰지 않음 (DESIGN.md 규칙 유지). 깜빡임은 큰 이슈 표시에만 |
| 움직임 줄이기 설정 | `prefers-reduced-motion`이면 깜빡임 대신 굵은 테두리 + 아이콘 |
| 같이 보이는 곳 | 배치도·라인 흐름·3D 뷰의 해당 설비, 알림, 토스트 |

## 6. 시안 계획

> **2026-11-19 바뀜 (D-103·D-104)**: 사용자 피그마 구상(`docs/wireframes/figma-구상/`)이 기본 방향이 됐고 대시보드는 3D가 기본이다. 그래서 1차 배치안 A·B·C(정적 HTML)는 만들지 않고, **피그마 골격 + UI 개선안(핵심 숫자 하나, 예지보전 영역, 조치 요청, 고장만 깜빡임, 이상만 색)을 Vue 앱에 바로 만든다**. 3D(12단계)를 앞당겼다. 아래 6.0~6.1은 당시 계획 기록으로 둔다.

### 6.0 두 번에 나눠 비교 (D-99)

배치와 톤을 동시에 바꾸면 어느 쪽 덕분에 좋아졌는지 가려낼 수 없다. 가장 무겁게 보는 두 기준(목적·가독성)은 배치에서 갈리므로 배치를 먼저 고른다.

| 차수 | 무엇을 바꿈 | 고정 | 화면 | 위치 |
|---|---|---|---|---|
| **1차 배치안** | 배치: 주인공 칸, 알림 위치·크기, 계층 묶는 방식, 숫자 띠·요약 열, 화면 나누기 | 무채색 + 상태 4색, 같은 토큰, 같은 글자 단계 | SCR-001 · 010 · 002-3 × 배치안 3개 + 기준안 B | `docs/wireframes/후보-v2/배치/` |
| **2차 톤** | 색·글꼴·선·밀도 (아래 6.1 표의 시안 1~3) | 1차에서 고른 배치 | SCR-001 (큰 이슈 장면) | `docs/wireframes/후보-v2/톤/` |

아래 6.1의 시안 1~3은 2차 톤 비교에 쓴다. 6.2~6.4는 두 차수 모두에 적용한다.

### 6.1 시안 3개 + 기준안 [Q-24 → D-98]

| 시안 | 바탕 디자인시스템 | 성격 | 예상 모습 |
|---|---|---|---|
| **기준안 B** | (지금 DESIGN.md) | 도면 위의 관제반 | 지금 그대로. 비교 기준이자 피드백 대상 |
| **시안 1 · 산업형** | Siemens iX + ISA-101 | 현장 관제 화면에 가장 가까움 | 중립 바탕, 이상 상태에만 색, 설비 계층 묶음, 고장 깜빡임 |
| **시안 2 · 분석형** | IBM Carbon (+ SAP Horizon 의미 색) | 엔터프라이즈 분석 화면 | 엄격한 그리드, 차트·숫자 위계가 뚜렷함, 표 중심 |
| **시안 3 · 제품형** | Linear·Vercel 계열 DESIGN.md | 가장 "세련된" 쪽 | 무채색, 얇은 선, 넓은 여백, 정보량은 적게 |

**세 시안 모두 지키는 것**
- **(핵심, D-96)** 화면마다 목적 한 줄과 주인공 칸. 가독성을 위해 배치부터 다시 짠다 (피드백 5)
- 상태 4색의 의미(D-77), 상태는 색 + 글자로 표시
- 그라데이션·빛 번짐·반복 애니메이션 없음 (D-93). 예외는 2.3 고장 깜빡임뿐
- 글자 단계 = 제목 / 본문 / 보조 + 숫자 2단계 (피드백 1)
- 화면 안 정보를 공장 > 라인 > 공정 > 설비 계층으로 묶는다. 메뉴는 그대로 (피드백 2, D-97)
- 알림은 작게, 대시보드 주인공은 공장 상태 (피드백 3)
- 고장(D) = 깜빡임 + "조치 요청" 버튼(시뮬레이션 상태 변경). 예지보전은 별도 영역 (피드백 4, D-97)

### 6.2 시안을 만들 화면 [가정: Q-27]
| 화면 | 고른 이유 |
|---|---|
| SCR-001 대시보드 | 공장 배치도·생산·OEE·알림이 모두 있음. 2D↔3D 전환 자리. 피드백 3·4·6이 가장 많이 걸리는 화면 |
| SCR-010 라인 상세 | 설비 흐름 + 요약 열. 트리에서 라인을 고르는 흐름 확인 |
| SCR-002-3 프레스 상세 | 관리값 그래프·설비 카드·비가동 이력. 공정 상세의 대표 |

**큰 이슈 장면을 꼭 넣는다**: 세 화면 모두 "L2 프레스 3단 고장" 장면으로 만들어 깜빡임·조치 요청·알림이 어떻게 보이는지 비교한다. 같은 장면에 예지보전 주의 설비도 하나 두어 별도 영역이 고장과 헷갈리지 않는지 본다. mock 시나리오에 이미 있다.

**화면 구성 실험 (이번 개편의 중심, D-96)**: 시안은 색·글꼴만 바꾼 것이 아니라 **배치 자체를 다르게** 만든다. 시안마다 "이 화면의 목적을 무엇으로 보고, 그래서 무엇을 크게 두었는지"를 시안 위에 한 줄로 적는다. 예를 들어 알림 위치와 크기, 요약 열과 상단 숫자 띠, 라인 상세를 대시보드 안으로 합치기 등. 다만 화면정의서의 **항목과 이벤트는 빠짐없이** 들어가야 한다.

### 6.3 시안 형식
- HTML 정적 시안. 데이터는 지금 `docs/wireframes/후보/data.js`나 mock 값을 쓰고, 화면에 "데모 값"이라고 표시한다.
- 위치는 `docs/wireframes/후보-v2/{시안}/{화면}.html` [가정].
- 비교 페이지 하나에 기준안 B와 시안 1~3을 같은 화면끼리 나란히 놓는다.
- 확인 크기는 FRONTEND.md 7장 기준: 1920×940(기준), 1536×730, 1440×810.

### 6.4 비교 기준 (사용자가 고를 때)
| 기준 | 질문 | 피드백 |
|---|---|---|

**가장 무겁게 보는 기준은 "목적이 드러나는가"와 "글자 읽기"(가독성)다 (D-96).** 나머지 기준이 좋아도 이 둘이 약하면 고르지 않는다.
