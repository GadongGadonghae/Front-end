# 백엔드 API 명세 v3.1 ↔ 프론트 차이

| 일자 | 기준 | 내용 |
|---|---|---|
| 2026-11-17 | 백엔드 `docs/api-spec-v3.1.md`, 프론트 `feat/vue-base` (`ca54ecc`) | 첫 작성 |
| 2026-11-17 | 〃 | 1.1~1.3 추가: 프론트에만 있는 것 · 백엔드에만 있는 것 · 둘 다 있지만 다른 것 |

> 비교 대상
> - **백엔드**: `docs/api-spec-v3.1.md` (REST 41개, WebSocket 4채널, MQTT 5개). 이 문서는 "Notion v0.2는 더 이상 기준이 아님"이라고 적고 있다.
> - **프론트**: 데이터 계약 `src/data/contracts.ts`(화면이 아는 유일한 인터페이스)와 그 근거인 `docs/specs/API명세서.md` v0.2, 화면정의서·기능명세서·결정사항(D-xx).
>
> 지금 프론트 화면은 모두 데모 공급기(`src/data/mock/`)로 돈다. 실제 API를 붙이려면 `src/data/api/`에 계약을 구현하는 어댑터를 만들면 되고 화면 코드는 바꾸지 않는 구조다(FRONTEND.md 6장). 아래 차이는 **어댑터로 메울 수 있는 것**과 **백엔드에 API·필드가 없어 결정이 필요한 것**으로 나눴다.

## 1. 한눈에 보기

| 구분 | 차이 | 영향 |
|---|---|---|
| **화면 범위** | 백엔드는 Vue 화면을 "모니터링·가동률 2개 + 로그인·사용자 관리"로 적는다. 프론트는 화면정의서의 화면 전체(SCR-000~011, 3D 제외)를 만들었다 | 리포트·생산 조회·예지보전·설정 화면의 API 상당수가 백엔드에 없다 (4장) |
| **식별자** | 라인 `L1~L6` ↔ `A~F`, 설비 `L1-PRS-1` ↔ `A-PR1`, 공정 `A~F` ↔ `COIL·SLITTING…` | 어댑터에서 바꾸면 된다. 화면 글자("L1")를 "A라인"으로 바꿀지는 결정 필요 |
| **설비 상태** | 백엔드에 `DC`(통신 끊김)가 5번째로 있다. 겹칠 때 순서도 다르다 | 상태 색이 4색(D-77)뿐이라 DC 색·표시를 정해야 한다 |
| **비가동 코드** | 프론트 7개 ↔ 백엔드 11개, 이름 체계가 다르다 | 코드 표를 하나로 맞춰야 한다 |
| **관리값 항목** | 프론트는 데이터셋 이름("Pressure 1"), 백엔드는 camelCase(`pressureLeft`). 기준도 프론트는 설비 **종류별**, 백엔드는 **설비별** | 설정 화면(SCR-009) 구조가 달라진다 |
| **처리 시간** | 프론트 데모는 표준CT 120초(라인 하루 200개), 백엔드는 프레스·용접 17초(라인 시간당 약 211개) | 데모 수치와 목표·계획 값이 실제와 크게 다르다 |
| **생산 목표** | 프론트는 공장 하루 목표 1개, 라인 계획 = 목표 ÷ 6 (D-87). 백엔드는 라인별 `planQty` (G-02·G-03) | 생산 목표 화면(SCR-008)과 달성률 계산이 달라진다 |
| **알람** | 프론트의 "알람"은 고장(D) 상태 이력. 백엔드의 `alarm`은 관리값 이탈 기록(등급 WARNING/CRITICAL, 확인 처리) | 같은 말을 다른 뜻으로 쓴다. 용어부터 맞춰야 한다 |
| **계획수정(재배정) 보고서** | 프론트는 사람이 [만들기]를 누르면 그때 계산(D-68). 백엔드는 정지 30분 이상이면 자동 생성, 계산식도 다르다 | 보고서 화면(SCR-007) 내용이 달라진다 |
| **실시간** | 프론트는 1초 스냅샷 전체 + 10초 요약을 받는 구조. 백엔드는 바뀐 설비만 보내는 W-01과 출고 카운트 W-03 | 어댑터가 W-01로 상태를 모으고, 라인 실적·요약은 주기 조회로 채워야 한다 |
| **예지보전** | 프론트 SCR-004 전체가 위험도(%)를 쓴다. 백엔드에 위험도 계산·API가 없다 | 예지보전 화면은 실제 데이터로 못 띄운다 |

## 3. 식별자와 코드

### 3.1 라인 · 설비 · 공정

| 대상 | 프론트 | 백엔드 | 비고 |
|---|---|---|---|
| 라인 | `L1`~`L6` | `A`~`F` | 화면 표기("L1"·"A라인")를 무엇으로 할지 결정 필요. 용어집은 L1~L6 |
| 도장 구역 | 라인 `PT` (라인 탭에 "도장") | 라인 없음, 설비 `PT1`·`PT2` | 프론트는 도장을 라인처럼 다룸(SCR-010 도장 탭) |

| 슬리터 | `L1-SLT` | `A-SL` | |
| 프레스 | `L1-PRS-1`~`4` | `A-PR1`~`4` | |
| 용접 | `L1-WLD` | `A-WD` | |
| 도장 | `PT-PNT-1`·`2` | `PT1`·`PT2` | |
| 비전 | `CM-VIS` | `VI` | |
| 공정 | `A` 코일입고 · `B` 슬리팅 · `C` 프레스 · `D` 용접 · `E` 도장 · `F` 출고 | `COIL` · `SLITTING` · `PRESS` · `WELDING` · `PAINTING` · `INSPECTION` | 프론트의 "출고(F)"가 백엔드의 "검사(INSPECTION)". 화면 이름은 출고 |

|---|---|---|
| 값 | `R` `S` `I` `D` | `R` `S` `I` `D` `DC` |
| 겹칠 때 대표 상태 | **D > I > S > R** (`lib/status.ts`) | **D > DC > S > I > R** |
| 색 | 4색 고정 (D-77) | DC 보라 (제안) |

- **DC**: 프론트 화면에 자리가 없다. 정할 것: 색(상태 4색·강조 파랑과 겹치지 않게), 글자("DC"·"통신 끊김"), 배치도·라인 흐름·범례·상태별 대수에 넣을지. 가동률에서는 R로 센다고 했으니 비가동 이력에는 나오지 않는다.
- **순서**: 라인 대표 상태를 정할 때 I(대기)와 S(정지) 중 무엇을 위로 볼지가 다르다. 프론트는 "대기가 정지보다 손실"이라 I를 위로 뒀다. 백엔드 순서로 맞출지 결정 필요.
- **I 판정 기준**: 백엔드는 "앞 구간 재공품이 0이면 I, 사유 `UP_SHORTAGE` 자동". 프론트 데모는 재공부족·작업지연 두 가지로 I를 만든다. 작업지연은 백엔드에서 사람이 고치는 사유(`UP_DELAY`)다.

### 3.3 비가동 사유 코드

| 프론트 (화면 이름) | 상태 | 백엔드 | 비고 |
|---|---|---|---|
| `planned` 계획정지 | S | `PL_SHIFT` 교대 · `PL_PM` 예방보전 · `PL_CHANGE` 모델 교체 | 백엔드가 셋으로 나눔 |
| `setup` 계획정지(셋업) | S | `PL_SETUP` 코일·나이프 교체 | |
| `starved` 재공부족 | I | `UP_SHORTAGE` | |
| `blocked` 작업지연 | I | `UP_DELAY` | 백엔드는 사람이 고칠 때만 |
| `fault` 장비고장 | D | `UP_BREAKDOWN` | |
| `fault-alarm` 장비고장(알람) | D | `UP_ALARM` | |
| `safety` 안전문제 | D | `UP_SAFETY` | |
| (없음) | | `UP_LABOR` 노사협의 ❓ · `UP_ETC` 기타 | 프론트 코드 표에 없음 |

- 백엔드 코드에는 화면 이름(한국어)이 없다. 화면 이름 표는 프론트(`lib/status.ts`)에 두면 되지만, `PL_SHIFT`·`PL_PM`·`PL_CHANGE`·`UP_LABOR`·`UP_ETC`의 한국어 이름과 상태(S/I/D)를 용어집에 추가해야 한다.
- 백엔드 사유는 상태와 1:1이 아니다(예: 계획정지 중 고장). 프론트는 "코드 → 상태"를 한 줄로 정해 두고 쓴다(`DowntimeCodeDef.state`).

### 3.4 관리값 항목과 기준

| 설비 | 프론트 항목 (DT-005·데이터정의서) | 백엔드 `metric` |
|---|---|---|
| 슬리터 | 출력 전류, 출력 토크, DC Link 전압 (+ 그래프용 지령·출력 주파수) | `torque` `current` `voltage` |
| 프레스 | Pressure 1, Pressure 2, Pressure 5 (합계), Press time | `pressureLeft` `pressureRight` `pressureTotal` `pressTime` |
| 용접 | 가압력, 전류, 전압, 통전시간 | `pressForce` `current` `voltage` `weldTime` |
| 도장 | pH, 온도, 전류 (+ 데모 건조로 온도) | `ph` `temperature` `current` `voltage` |

- **이름**: 화면에 보일 한국어 이름과 단위 표가 필요하다. 백엔드 M-03은 `unit`을 주지만 화면 이름은 주지 않는다.
- **단위·스케일**: `pressTime`은 0.01초 단위(551 = 5.51초). 프론트는 ms로 표시하고 기준을 50~2,000으로 두었다. 화면에 어떤 단위로 보일지 정해야 한다.
- **기준 단위**: 프론트는 설비 **종류별** 하한·상한(같은 종류 모두 같은 기준, SCR-009 "종류 고르기 → 표"). 백엔드는 **설비별** 기준치(M-10에 `equipmentId`, M-11은 1건씩 수정). 설정 화면을 설비별로 바꿀지, 종류별로 한 번에 저장하는 API를 둘지 결정 필요.
- **수정자**: 프론트 설정 화면은 항목마다 "마지막 수정 시각·수정자"(D-73)를 보인다. M-10·M-11 응답에 `updatedAt`만 있고 수정자가 없다.
- **슬리터 실설비(D-43)**: 프론트 공정 상세 슬리팅은 인버터 운전·방향·지령/출력 주파수·RPM·최근 트립을 보인다. 백엔드 슬리팅 값은 torque·current·voltage뿐이다.

## 5. 개념이 다른 것

### 5.1 생산 목표와 라인 계획

- **프론트(D-17·D-71·D-87)**: 공장 전체 하루 목표 1건(예: 1,200). 라인 계획 = 목표 ÷ 가동 라인 6. 지난 날짜는 잠금, 목표가 없으면 "목표 미설정"(D-72).
- **백엔드(G-02·G-03)**: 날짜·라인마다 `planQty`(예시 1,500).
- **결정 필요**: 공장 목표를 받아 백엔드가 라인으로 나눌지, 화면에서 라인별로 입력할지. 대시보드의 "목표·실적·달성률"도 이에 따라 바뀐다.

### 5.2 처리 시간과 생산 규모

- **프론트 데모**: 표준CT 120초 [가정](데이터정의서 4.1), 라인 하루 계획 200개, 공장 목표 1,200개.
- **백엔드**: 슬리팅 16초 · 프레스 17초(1대당) · 용접 17초 · 도장 4초 · 검사 7초. 라인 능력은 시간당 약 211개.
- 데모 수치(목표·계획·실적)를 백엔드 처리 시간에 맞춰 다시 정해야 한다. 데이터정의서 4.1 표준CT도 갱신 대상이다.

### 5.3 계획수정(재배정) 보고서

| | 프론트 (FN-009, D-68·70·83) | 백엔드 (R-01·R-02) |
|---|---|---|
| 만드는 때 | 고장(D) 건에서 사람이 [보고서 만들기] | 정지 30분 이상이면 자동 |
| 부족 수량 | 그 라인이 자정까지 만들 예정이던 남은 라인 계획 | 손실 수량 = 정지 시간 × 라인 능력(시간당 211개) |
| 나누는 법 | 다른 정상 라인의 남은 능력(남은 시간 ÷ CT − 남은 계획) 비율대로 | 여유 라인 추천 (`spareCapacity`, `addQty`). 식은 명세에 없음 |
| 도장·비전 고장 | 도장은 다른 1대로, 비전은 대체 없음(전량 미달) | 언급 없음 |
| 결과 | "목표 달성 가능" / "목표 미달 예상 N개" | 없음 |

| PDF | 있음 (D-30) | 없음 |

→ 어느 쪽 규칙으로 갈지 결정 필요. 지금 프론트 화면은 FN-009 계산 결과(남은 계획·비율·미달 예상)를 보이도록 만들어져 있다.

### 5.4 "알람"이라는 말

- **프론트**: 알람 = 고장(D) 발생(FN-005). 토스트·헤더 종·알림 열·"알람·비가동 이력" 화면이 이 뜻이다.
- **백엔드**: `alarm` = 관리값 이탈 기록(등급 WARNING/CRITICAL, 확인 처리 M-06). 고장 전체는 `downtime_event`.
- 프론트에 없는 것: 알람 **등급**, **확인(ack)** 처리 화면. 백엔드에 없는 것: 고장 알림의 **메일·슬랙 발송 결과**(D-63).

### 5.5 계획정지(S)

- **백엔드**: 사람이 S-02로 라인 계획정지를 시작하고 S-03으로 끝낸다. 그 사이 라인 설비 6대가 S.
- **프론트**: 계획정지를 시작·종료하는 화면이 없다. S는 데이터로 들어온다고 보고 표시만 한다.
- **결정 필요**: 계획정지 시작·종료 버튼을 어느 화면에 둘지 (라인 상세가 자연스러움).

### 5.6 도장 경로

- **백엔드**: 라인마다 기본·현재 도장 설비(`defaultPaintId`·`currentPaintId`, C-04)와 경로 전환 M-09(P1).
- **프론트**: 라인 → 도장 2대가 공용이라고만 그린다. 경로·전환 화면이 없다. 배치도의 도장 연결선과 공정 상세 "라인별 받은 수"에 경로를 반영할지 결정 필요.

## 7. 결정·확인할 것

### 백엔드에 요청 (API·필드)

1. 시간대별 생산 누적 (대시보드·라인 상세 그래프): `unit=hour` 또는 오늘 시간대별 API
2. 제품 내역·제품별 공정 기록 (생산 조회 SCR-011): 목록(검색·결과 거르기·50건) + 상세
3. 공정 검사 불량 제품 목록 (공정 상세): 시각·제품 ID·설비·사유
4. 예지보전 위험도 (SCR-004): 설비·항목별 % 목록 + 위험 진입·해제 이력. 안 만들면 화면을 빼야 함
5. 고장 알림 메일·슬랙 발송 결과 (D-63): U-08 응답에 필드
6. 라인 대표 상태 타임라인 (가동률): 라인 단위로 합친 U-12
7. 모든 목록 응답에 `totalElements`
8. 오류 `code` 목록 (최소: 지난 날짜 목표 저장, 하한>상한, 없는 설비)
9. 관리값 기준 수정자(`updatedBy`)
10. 코일 입고 기록·재고 추이 (공정 상세 코일입고)
11. 설비별 오늘 사이클 수·평균 CT (프레스 단별, SCR-002-3)

### 함께 정할 것

1. 화면 범위: 백엔드 문서의 "화면 2개"와 화면정의서(SCR-000~011) 중 무엇이 기준인지
2. 화면 표기: 라인 `L1`·`A`, 출고·검사
3. `DC` 색·표시와 대표 상태 순서(I와 S)
4. 비가동 코드 표 통합 (한국어 이름·상태 포함, 용어집 갱신)
5. 생산 목표: 공장 1개 vs 라인별
6. 재배정 보고서 규칙: FN-009 vs 백엔드 자동·손실 수량식, PDF
7. 관리값 기준: 종류별 vs 설비별, 항목 화면 이름·단위(`pressTime` 0.01초)
8. 조치 담당자: 로그인 사용자 자동(D-84) vs `actionUserId` 지정, 사유 수정 허용 여부(D-33)
9. 도장 경로 전환·계획정지 시작/종료 화면 위치
10. 실시간: 라인별 실적 푸시가 필요한지(대시보드 1초 갱신), 아니면 주기 조회로 충분한지

### 프론트에서 할 일 (결정 뒤)

- `src/data/api/` 어댑터: 주소·JWT·ID/코드 변환·페이지 형식 변환·여러 API 합치기
- `types/state.ts`: `DC` 추가, 비가동 코드 표 교체
- 관리값 항목 이름·단위 표, 설정 화면(종류별/설비별)
- 데모 수치를 백엔드 처리 시간 기준으로 다시 정함
- 백엔드에 없는 기능(예지보전 위험도, 제품 내역 등)은 결정에 따라 화면에서 빼거나 "준비 중"으로 표시
