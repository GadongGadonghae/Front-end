# 실시간 웹소켓 전환 — W-01 · W-03 · W-04 · W-05

| 일자 | 내용 |
|---|---|
| 2026-11-22 | 첫 작성. 백엔드 `feat/ws-allowed-origins` (`086531e` · `db05a5e`) · 프론트 `feat/vue-base` (`5614a10`) 구현 기준 (D-122) |

> **이 문서의 용도**: 1초마다 묻던 실시간 값을 웹소켓으로 "바뀔 때만" 받게 바꾼 내용, 어디에 구현돼 있는지, 서버 PC에서 무엇을 해야 하는지, 잘 되는지 어떻게 확인하는지를 한곳에 모은 것.
> **누가 읽나**: 실시간 화면을 고치는 프론트 담당, 백엔드를 실행하는 담당(설정은 5장, 확인은 6장).

## 1. 무엇을 바꿨나

| 구분 | 전 | 후 |
|---|---|---|
| 실시간 값 받기 | 화면마다 REST를 주기적으로 물어봄 (상태 1초 3건, 물류 1초 2건, 알람 2초, 관리값 2초) | 앱이 켜질 때 웹소켓 연결 **하나**를 맺고, 서버가 **바뀔 때만** 보냄 |
| 백엔드 웹소켓 | 서버는 열려 있었지만 프론트가 구독하지 않음. 허용 화면 주소는 `localhost:5173` 하나 | 프론트가 구독. 허용 주소는 설정값(개발 · 미리보기 · IP 접속 · nginx 배포) |
| 채널 | W-01 · W-03만 실제로 보냄 | W-04 설비 공정 값, W-05 3D 물류 추가 |
| 끊겼을 때 | - | 자동으로 원래 주기 조회로 돌아감. 다시 붙으면 REST로 채우고 재구독 |

- **기존 REST는 하나도 바꾸지 않았다.** 새 채널은 같은 데이터를 웹소켓으로도 보내는 것이라 원래 동작에 영향이 없다.
- 백엔드가 꺼져 있거나 허용 주소가 아니어도 화면은 지금처럼 돈다 (주기 조회로 대체). 그래서 **화면이 돈다고 웹소켓이 되는 것은 아니다** → 확인은 6장.

## 2. 채널

`/ws`에 STOMP로 연결하고 필요한 주소만 구독한다 (SockJS 없음).

| ID | 구독 주소 | 백엔드가 보내는 때 | 프론트가 쓰는 곳 |
|---|---|---|---|
| W-01 | `/topic/status` | 판정에서 설비 상태(R · S · I · D · DC)가 **바뀐 설비만** | 스냅샷(배치도 · 3D · 라인 상세), 알람 확인 시점 |
| W-02 | `/topic/alarms` | **보내지 않음** (알람을 만드는 로직이 백엔드에 없음) | 쓰지 않음 (아래) |
| W-03 | `/topic/production` | 판정할 때마다 오늘 누적 (같은 값이 다시 올 수 있음) | 공장 실적, 라인별 실적 다시 받기 신호 |
| W-04 | `/topic/metrics/{설비ID}` | 1초마다, **새 점이 있을 때만**. 그 설비를 구독한 화면이 있을 때만 계산 (11/22 추가) | 공정 상세 관리값 그래프 |
| W-05 | `/topic/flow` | 1초마다. 구독한 화면이 있을 때만 계산 (11/22 추가) | 3D 물류 (제품 위치 · 코일 재고) |

- **W-02를 쓰지 않는 이유**: W-02는 관리값 이탈 알람(`alarm` 테이블)이고, 화면의 알람(고장 토스트 · 알림)은 비가동 이벤트(U-08)다. 데이터가 다르다. 또 `alarm` 테이블은 지금 시연용 생성 스크립트만 채우고 AI 원인 추적 점수(직접 신호 40점)가 그 값을 쓰므로, 판정이 알람을 만들기 시작하면 리허설 결과가 바뀐다. 화면 알람은 W-01로 충분하다 (3장).
- **요약 채널은 없다**: 오늘 요약(`live.onSummary`, 16건)은 그대로 10초 조회. 줄이려면 백엔드에 "한 번에 주는 API"를 따로 요청한다 (8장).

메시지 모양은 백엔드 `docs/api-spec.md` WebSocket 절. W-04는 M-03 `metrics` 모양 그대로, W-05는 M-17 `at` · `products` + `coilStockQty`(M-16 재고, 제품 수).

## 5. 실행 · 설정

### 5.1 허용 화면 주소 (백엔드)

브라우저 **주소창의 주소**가 들어간다. 백엔드 주소가 아니다. 개발 서버의 `/ws` 중계를 거쳐도 이 값은 바뀌지 않는다.

```yaml
# application.yml (기본값). [*] = 아무 포트, 포트 없는 주소(nginx 80)도 포함
websocket:
  allowed-origin-patterns: '${WS_ALLOWED_ORIGINS:http://localhost:[*],http://127.0.0.1:[*],http://192.168.0.*:[*],http://192.168.203.*:[*]}'
```

- 서버 PC 대역이 다르면 환경 변수 `WS_ALLOWED_ORIGINS`로 바꾼다. 예: `http://localhost:[*],http://10.0.0.*:[*]`
- https 도메인으로 배포하면 그 주소(`https://…`)를 추가한다.
- REST는 이 검사를 하지 않는다. 그래서 REST는 되는데 웹소켓만 403이 나면 이 값을 본다.

### 5.2 프론트

| 설정 | 값 |
|---|---|
| `VITE_DATA_SOURCE` | `api` (데모 공급기는 웹소켓을 쓰지 않음) |
| `VITE_WS_URL` | 기본 `/ws`. 상대 경로면 지금 화면 주소 기준(`ws://호스트/ws`)으로 붙음 |
| `vite.config.ts` | `/ws` 중계(`ws: true`)는 원래 있음. 미리보기(4173)도 같은 중계를 씀 |
| 라이브러리 | `@stomp/stompjs` 7.5 추가 → 브랜치를 바꾼 PC는 **`npm install` 필수** |

### 5.3 서버 PC에서 바꿔 띄우기

```bash
# 백엔드: 기존 서버를 끄고
git fetch && git switch feat/ws-allowed-origins
./gradlew bootRun

# 프론트
git fetch && git switch feat/vue-base && git pull
npm install
npm run dev -- --host        # 미리보기로 띄우면 npm run build 를 다시
```

DB · Node-RED · `application-local.yml`은 바꿀 것이 없다.

### 5.4 nginx로 배포할 때

`/ws`를 백엔드로 넘기면서 웹소켓 업그레이드 헤더(`Upgrade` · `Connection`)를 붙여야 한다 (`infra/배포계획서.md`에 적혀 있고 설정 파일은 아직 없음).

## 6. 잘 되는지 확인

1. 브라우저 F12 → **Network → WS** 탭: `/ws`가 **101**.
2. 그 연결의 **Messages**:
   - 처음 `CONNECTED`
   - 대시보드: `/topic/flow` 1초마다, `/topic/production`, 상태가 바뀔 때 `/topic/status`
   - 공정 상세: `/topic/metrics/설비ID`
3. **Fetch/XHR** 탭: `monitoring/status` 요청이 1초마다 → 10초마다, `flow/positions`는 화면을 열 때 한 번.

## 7. 안 될 때

| 증상 | 원인 · 조치 |
|---|---|
| `/ws` 403 | 화면을 연 주소가 허용 목록에 없음 → 5.1 `WS_ALLOWED_ORIGINS` 후 백엔드 재시작 |
| `/ws`가 계속 실패 · 3초마다 다시 시도 | 백엔드가 이전 브랜치로 떠 있음, 또는 꺼져 있음. 화면은 주기 조회로 계속 돈다 |
| `/topic/status`가 거의 안 옴 | 정상. 상태가 바뀔 때만 보낸다 |
| `/topic/metrics/…`가 안 옴 | 새 공정 값이 없으면 보내지 않는다 (재생기 · 수집이 돌고 있는지 확인) |
| 프론트 실행 시 `@stomp/stompjs`를 못 찾음 | `npm install`을 안 함 |

## 8. 남은 것 · 한계

| 항목 | 상태 | 비고 |
|---|---|---|
| 실제 서버에서 연결 확인 | 안 함 | 작업 PC에서 백엔드 · DB를 띄우지 않았다. 6장 방법으로 서버 PC에서 확인 |
| 백엔드 테스트 2개 실행 | 안 함 | 컴파일만 확인. `./gradlew test --tests '*WebSocketOriginTest' --tests '*LivePushServiceTest'` |
| 요청 수 전후 측정 | 안 함 | `npm run perf`의 "요청 수"는 서버 없이 재는 방식이라 웹소켓이 붙지 못하고 주기 조회로 돌아간다 → 효과가 잡히지 않음. 서버에 붙인 화면에서 Network 탭으로 1분 요청 수를 전후 비교할 것 |
| 오늘 요약 16건 | 그대로 10초 | 백엔드에 "요약을 한 번에 주는 API" 요청이 가장 효과가 큼 (웹소켓 없이도 줄어듦) |
| W-02 알람 | 쓰지 않음 | 2장 이유. 화면 알람은 W-01로 대체 |
| 웹소켓 로그인 검사 | 없음 | `/ws`는 인증 없이 열려 있다. 허용 주소를 사내망 대역으로 좁혀 둔 이유 |
| 구독 유지(D-120)와 함께 동작 | 서버에서 확인 필요 | 화면을 옮겨도 구독을 2초 유지하는 `sharedLive.ts` · `usePoll.ts` 위에서 웹소켓 구독도 같이 유지되는지, 화면 전환 때 `/ws` 구독 · 해제가 반복되지 않는지 6장 방법으로 볼 것 |
